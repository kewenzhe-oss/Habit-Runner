# 响应速度定位与下一批性能动作

日期：2026-10-21。范围：Habit Runner 当前工作区（`e171931` 加已有未提交设计改动）中的性能报告、基准脚本，以及 dashboard 页面、hooks、API、Session 链路。

本轮只做限定性能定位。没有修改产品代码、数据库、服务配置，没有启动或停止服务，没有运行会写入测试数据的基准脚本，也没有 push。工作区原有的 3 个组件修改和 2 份设计文档保持原样。

## 结论与证据边界

当前最大的三项性能风险是：

1. **页面切换仍没有真实的端到端基线。** 线上曾观察到今日页到历史页约 2.81 秒、历史页到设置页约 2.34 秒才出现目标正文；本地预热生产服务器上的完整 HTML 只有约 27–42ms。两者测量范围不同，不能相互换算。目前没有线上浏览器 trace、RSC 请求体积、客户端执行时间和数据库跨区耗时，因此不能认定那 2–3 秒由哪一层造成。
2. **历史页和今日页仍会读取约 120 天打卡，历史页还分两个阶段读取。** 这是代码已确认的数据路径；它是否构成线上主要耗时仍是推测，必须用查询行数、SQL 耗时和浏览器 trace 验证。历史页先等待事项和 112 天窗口数据，再单独读取 120 天 streak 数据，是明确的额外等待边界。
3. **打卡的“页面先响应”和“服务器已持久化”是两条不同时间线。** 当前列表会先乐观变色，再等待写入 API；写入成功后还要在返回响应前计算 streak。现有本机基线只测了待办保存，没有测习惯打卡的浏览器反馈、POST 持久化确认或失败回滚。不能把乐观更新当成已保存，也不能把旧报告的 5.2ms 当成打卡 INP。

这三项优先处理页面切换和打卡。分类筛选、弹窗打开、详情图表、冷启动和数据库区域也有候选风险，但现有证据不足以把它们排在上述三项之前。

## 已测事实、静态证据与推测

### 已经测量或可直接核对的基线

历史报告 `docs/ui-ux-performance-results-2026-10-20.md` 和 `docs/ui-ux-performance-local.json` 记录的是：本机、隔离的 `habit_runner_perf` PostgreSQL、预热后的生产服务器，每项预热 2 次、取 7 个样本。

| 指标 | 修改前中位数 | 修改后中位数 | 可以得出的结论 |
| --- | ---: | ---: | --- |
| 今日 API | 14.5ms | 13.4ms | 本机热请求不是当前的显著绝对耗时 |
| Dashboard 完整 HTML | 28.2ms | 27.1ms | 本机服务器读取基本不变 |
| 历史页完整 HTML | 40.7ms | 41.8ms | 历史读取没有加速，仍是最慢的本地 HTML 基线 |
| 设置页完整 HTML | 9.7ms | 13.8ms | 设置读取反而略慢 |
| 待办保存至数据就绪 | 16.5ms | 5.2ms | 优化移除了保存后的整页重取 |
| 能量保存至数据就绪 | 24.0ms | 3.1ms | 优化移除了保存后的 Dashboard 重取 |

这些数字的边界很重要：

- 它们是 loopback HTTP 墙钟，没有网络 RTT、浏览器导航、JS 下载与执行、React 渲染或下一帧绘制。
- 待办测试是 PATCH 请求完成；能量测试是 PUT 请求完成。它们不是习惯打卡。
- 脚本会修改隔离测试库中的待办和能量，完成后尝试恢复待办和能量。本轮数据库未运行，未重跑脚本。
- 旧报告没有保存原始 HTML、RSC 传输体积、请求瀑布或浏览器 trace，无法进一步拆出 2.81 秒和 2.34 秒的构成。

本轮额外读取了已有的 `.next` 构建产物，只计算文件体积，没有启动服务：

| 路由 | 客户端脚本，按当前 manifest 去重后 gzip | 当前页面自身 chunk gzip | 页面自身 chunk Brotli |
| --- | ---: | ---: | ---: |
| Dashboard | 约 275.6KB | 约 36.6KB | 约 29.9KB |
| 历史 | 约 245.7KB | 约 10.7KB | 约 9.4KB |
| 设置 | 约 250.0KB | 约 5.4KB | 约 4.7KB |

这些是按 manifest 静态汇总的体积，不是线上实际传输量。它们没有证明页面切换慢是 bundle 造成，但说明需要把共享资源与路由 RSC 请求分别测量，不能只看页面 chunk。

### 当前代码的静态证据

**共享布局和 Session**

- 登录后的页面已共用 `app/(app)/layout.tsx`，`AppLayout` 只在共享布局中读取用户，避免了此前每个子布局各自重建导航。
- `getCurrentUser()` 使用 React `cache`，同一服务器渲染中的页面读取可以复用；`lib/auth.ts` 的 JWT 回调在 token 已有 `id` 时不再查询用户表。
- 这些结论只说明重复布局和重复用户读取已经减少，不说明导航已经快。没有线上 RSC 请求或浏览器 trace，无法判断剩余等待在哪里。
- `apphosting.yaml` 仍配置 `minInstances: 0`。空闲后的冷启动是真实候选，但当前没有实例启动时间、冷/热对比或线上服务端日志，属于**推测**。

**历史页**

- `app/(app)/insights/page.tsx` 先等待用户和日期，再等待 `getActivityHistoryData()`，目标正文没有独立于数据读取的流式内容。
- `lib/api/history.ts` 第一次读取事项，然后并行读取 112 天打卡、全时段日期聚合、已完成待办、最早打卡和最近 6 条记录。
- 随后又单独读取约 120 天的 streak 数据，再为每个习惯进行内存计算。这里没有每个习惯一条 SQL 的 N+1，但存在第二个读取阶段和全量历史行的传输、解析与分桶。
- 历史页目前只有共享 `loading.tsx`，没有把数据区块拆成可独立出现的流式边界。摘要组件本身是客户端组件，即使服务端先送出它的外壳，也要等待 hydration 才能成为可交互内容。加载骨架能缩短“看到反馈”的时间，不会自动缩短数据完成时间。
- 现有本机历史 HTML 41.8ms 相对其他页面最慢，但没有数据库 SQL 耗时和浏览器执行数据，不能把 120 天读取认定为线上 2.34–2.81 秒的主因。

**今日页**

- `lib/api/checkin.ts` 已把能量、事项、本周打卡和 120 天打卡的读取并行化，这是已经实施的优化。
- 今日页仍把所有约 120 天打卡行读出后建立每事项分桶，再对每个事项执行内存 streak 计算。`Promise.all` 只并行 I/O，不会消除传输、解析、分桶和渲染成本。
- 今日 API 已有 `Server-Timing` 的 `auth` 和 `dashboard` 分段。它能直接给出服务器内部两段耗时，但还没有细分“事项读取、120 天读取、DTO 计算、序列化”。
- 当前 `.next` 的 Dashboard 客户端脚本按 manifest 去重后约 275.6KB gzip。它是否造成页面切换等待，需要浏览器 trace 和实际 Network 传输体积验证。

**打卡**

- `components/dashboard/habit-item.tsx` 在点击戒除状态、待办状态时先通过 `mutateItem()` 更新列表；`record-action-modal.tsx` 保存习惯时也会先显示乐观状态。
- `hooks/use-dashboard-items.ts` 为每个事项维护 pending 状态，阻止同一事项重复写入；失败时恢复旧对象。这样可以改善即时反馈，但乐观状态还不是服务器确认。
- 习惯打卡 POST 进入 `recordHabitCheckIn()` 后，先读取事项并校验归属与类型，再 upsert 打卡，再读取 streak 数据并计算，最后返回。待办 PATCH 也会先读事项，再在事务中写事项和打卡。
- 因此“点击后看到变化”通常早于“POST 返回 200”和“刷新后仍存在”。当前没有浏览器测量把这三段时间分开。
- 现有 5.2ms 是本机待办 PATCH 完成时间，不能代表习惯 POST，也不能代表线上持久化确认或失败恢复。

### 尚未证明、不能当成事实

- **推测：** 线上 2–3 秒主要来自数据库跨区 RTT、冷启动、RSC 下载、JS 执行或 React 渲染中的某一项。目前没有足够数据给它们分配占比。
- **推测：** 120 天读取是最大单项耗时。代码路径和本地历史页基线支持优先验证，但缺少 SQL 耗时和真实数据规模证据。
- **推测：** Dashboard 约 276KB gzip 的共享脚本导致点击后等待。需要比较冷/热导航的 trace、实际传输字节和脚本执行时间。
- **未知：** 分类筛选和弹窗在 hydration 完成后是否仍有明显主线程长任务。它们是本地状态变化，旧报告的操作耗时包含工具开销，不是浏览器 INP。
- **未知：** 详情页图表拆分能带来多少收益。现有报告没有把图表依赖计入首屏关键路径的运行时证据，不应先按 bundle 大小直接改。

## 三项最大瓶颈与直接验证方式

### 1. 页面切换端到端链路

**为什么先做：** 用户直接感知的页面切换仍是当前唯一存在秒级观察的用户路径，而且今日、历史、设置之间的差异能够帮助定位服务器、传输和客户端成本。共享布局、会话缓存和加载骨架已经存在，但仍没有证明端到端延迟下降。

**可直接验证的指标**

在同一账号、同一构建、同一网络和同一数据规模下，分别测试：

- `dashboard → insights`
- `insights → settings`
- `settings → dashboard`

每次记录：

1. `pointerup` 到导航 pending 可见。
2. `pointerup` 到目标正文标题可见。
3. `pointerup` 到目标页面可交互，并记录 INP 或交互延迟。
4. RSC/HTML 请求 TTFB、下载完成、压缩后传输字节和解析时间。
5. Dashboard 与历史 API 的 `Server-Timing: auth`、`Server-Timing: dashboard`，并补充事项读取和长历史读取分段。
6. 客户端 main-thread long task、hydration、React commit 和下一帧绘制。

测试条件必须固定：同一生产构建、同一测试账号与数据、移动端 4x CPU throttle、固定 Fast 4G 网络，至少预热一次后再做 15 次导航。分别保留冷实例和热实例结果，报告中位数、P95、最大值和失败率。浏览器 Performance trace 需要关联 Network、RSC 请求和长任务，不能只用导航总时间。

**直接验收**

- 页面正文出现前，共享导航不重新挂载。
- 首次反馈与最终数据完成分别计时；加载骨架出现的时间不能被当成正文就绪时间。
- 以同一份 trace 对照修改前后：目标正文可见时间、INP/P95、RSC 请求数与字节数、long task 总时长。
- 若仍慢，下一步应由 trace 中的主要区间决定：服务器等待、数据库 RTT、RSC 传输、脚本执行或 React 渲染。
- 不在没有数据的情况下预设固定百分比或固定毫秒收益。

**低成本候选动作**

- 给今日和历史数据读取增加不包含用户信息的细分 `Server-Timing`，先取得证据再改查询。
- 先确认历史页当前 loading 骨架和导航 pending 的实际首次反馈时间，再评估把摘要、图表和习惯列表拆成独立流式边界，缩短正文首次出现时间。
- 在浏览器数据证明路由 chunk 是主要等待后，再评估弹窗和图表等非首屏依赖的延迟加载；不要仅凭 bundle 大小改结构。

### 2. 历史页与今日页的 120 天读取和后处理

**为什么先做：** 今日页与历史页都是高频入口；两者都存在长历史读取。历史页的本地 HTML 基线最慢，且代码中有一段可明确识别的第二阶段读取。现有实现已经并行化部分查询，继续优化必须针对剩余的具体成本。

**可直接验证的指标**

- 对同一用户分别记录事项数量、112 天窗口打卡行数、120 天 streak 打卡行数、读取字节数和最终 DTO 数量。
- 用 Prisma 查询日志或 `EXPLAIN (ANALYZE, BUFFERS)` 只读检查三条关键查询：事项、窗口打卡、120 天 streak 打卡。记录执行时间、扫描行数、返回行数、是否命中 `check_ins(user_id, date)` 或 `check_ins(item_id, date)` 索引。
- 在 `getActivityHistoryData()` 和 `getTodayDashboardData()` 内部记录不包含用户信息的阶段计时：事项、窗口数据、120 天数据、分桶、streak、DTO 序列化。
- 浏览器侧记录历史页从请求开始到首段正文出现、摘要和图表可见、习惯列表可交互的时间。

数据量至少要覆盖小型和成熟账号两种条件，不能只用空清单或 19 个事项的本地种子证明结论。冷、热数据库分别记录，避免把首次连接成本算成查询成本。

**直接验收**

- 用同一数据集、同一构建比较：历史 API 总时间、首次数据阶段、第二阶段、返回行数、响应字节和浏览器列表可交互时间。
- 若 120 天读取被证明为主因，优先减少不必要的全量行、合并重叠日期窗口或按当前视图需要计算；若它只占很小比例，应保留现有查询并把预算转向浏览器或网络层。
- 今日页仍须保留本周 trace、昨日意图和 streak 的日期与排期语义；历史页仍须保留成熟账号的 16 周视图。性能改动不得用截断历史导致错误 streak。
- 不在本轮预设“改成 30 天”或“只取当前可见窗口”这类会改变产品语义的方案。

**低成本候选动作**

- 将历史页第二个 120 天读取与第一个窗口读取合并，或把依赖数据的部分移入独立流式边界；先测量，再决定是否值得实施。
- 对今日页的长历史读取增加行数和阶段耗时，确认并行读取之后的客户端与服务端处理是否仍显著。
- 分类请求只在分类变更时刷新。现有保存链路已不再普遍重抓整页，不应重新引入保存后全量刷新。

### 3. 打卡的即时反馈、持久化确认与失败恢复

**为什么先做：** 打卡是核心操作，也是“看起来完成”与“真正保存”最容易混淆的路径。当前乐观更新设计应当保留，但需要证明它的即时反馈没有掩盖长持久化等待，且失败后界面和数据库状态一致。

**可直接验证的指标**

对习惯打卡、戒除状态和待办完成分别记录：

1. 点击或提交到下一帧出现目标状态。
2. 提交到 pending/保存中状态可见。
3. 提交到写入 API 返回 2xx。
4. 提交到响应正文解析完成。
5. 提交到刷新页面或新请求能读到同一状态。
6. 模拟慢请求、非 2xx、网络中断和重复点击时，回滚、重试和锁定是否按预期工作。

持久化成功只能以服务器 2xx 且后续读取到同一权威状态为准。乐观变色、toast 文案和按钮 spinner 都不能单独作为成功证据。

测试应使用隔离数据库中的专用测试事项，并在每次采样前恢复到相同状态；恢复动作不计入结果。不要对线上真实用户记录做写入测试。记录服务端鉴权、事项读取、打卡 upsert、streak 读取与计算各自耗时，并关联浏览器 Network 和 Performance trace。

**直接验收**

- 报告“即时反馈中位数/P95”和“持久化确认中位数/P95”两组数字，不能合并成一个“打卡耗时”。
- 慢请求期间，界面必须明确显示保存中，同一事项不能重复提交；失败后恢复原状态并提供可重试的失败反馈。
- 保存成功 toast 或“已完成”视觉只能在服务器确认后作为最终成功状态；在确认前应明确为待保存。
- 优化响应体或 streak 计算时，只有持久化结果和后续读取一致才算成功。

**低成本候选动作**

- 为打卡写入增加 `Server-Timing`，先拆分鉴权、事项校验、写库和 streak 计算。
- 在已有乐观更新基础上明确 pending 与 confirmed 的视觉/文案状态，避免把本地乐观状态当成持久化成功。
- 只有测量证明 streak 的后置读取是显著阻塞时，才评估把展示指标改为惰性读取或返回已持久化的最小结果；不得牺牲归属校验和失败恢复。

## 复测与产物要求

本轮不新增或修改基准脚本。后续复测可以沿用 `scripts/benchmark-local.mjs` 的隔离数据库和 loopback 限制，但它只适合本机 HTTP 对照：

```sh
node --env-file=.env.local scripts/benchmark-local.mjs http://localhost:3001 http://localhost:3000 /tmp/habit-performance-direct.json
```

运行该脚本前需要用户明确授权启动隔离数据库和两个生产服务器，因为脚本会写入测试待办和能量。它不能替代以下浏览器证据：

- Performance trace，包含 Navigation、Network、RSC、long task 和绘制。
- 页面正文标题出现、可交互时间和 INP。
- 打卡点击到乐观反馈、API 2xx、持久化后读取一致的时间线。
- 冷实例和热实例分开的结果。

建议最终复测报告至少保存：

- 构建 ID、测试账号匿名标识、数据规模、浏览器与设备、网络和 CPU throttle。
- 每项 15 次样本的中位数、P95、最大值和失败率。
- 请求数量、压缩后传输字节、RSC/HTML 体积、`Server-Timing` 分段。
- 修改前后同条件 trace 和原始 JSON；没有保存原始数据的结果只能标为观察值。

## 建议的下一批顺序

1. **先建立页面切换和打卡的可信基线。** 取得 15 次样本、INP/P95、浏览器 trace、RSC/API 请求与 `Server-Timing`；记录冷/热实例和数据规模。
2. **按证据处理页面切换。** 如果 trace 指向历史数据等待，优化查询与流式边界；如果指向脚本或渲染，再拆分客户端依赖；如果指向冷启动或跨区 RTT，保留配置成本评估并报告具体证据。
3. **并行验证 120 天读取。** 记录行数、SQL 计划、阶段耗时和返回体积，只改变被证明的主要阶段。
4. **完善打卡状态语义。** 保留乐观更新和失败回滚，明确待保存/已保存，禁止用视觉成功替代持久化确认。
5. **最后处理次要候选。** 分类筛选、弹窗首次打开和详情图表在 hydration 后的浏览器 trace 显示为显著长任务时再改；目前没有足够证据将它们列在前三项。

| 项目 | 状态 | 可用范围 |
| --- | --- | --- |
