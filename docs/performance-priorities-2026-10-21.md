# 响应速度优先原则

用户于2026-10-21明确：整个应用响应速度是主要优化流程。

设计变更以减少操作步骤和首屏渲染负担为前提。避免为装饰添加动画库、额外字体或复杂背景。

## 验证顺序

1. 生产构建下记录导航点击至内容可交互、打卡点击至反馈、打卡至服务端确认，分开计时。
2. 比较冷/热加载、移动端CPU和网络节流，报告中位数与P95、失败率、请求数量、传输体积。
3. 浏览器trace关联Network与Server-Timing；区分数据库跨区延迟、冷启动、请求串行、JS解析与渲染。
4. 一次修改一个已定位瓶颈，保持同数据、同网络、同构建条件复测。

## 当前已知限制

历史报告docs/ui-ux-performance-results-2026-10-20.md仅为本机热生产HTTP基线，不等同线上INP或页面可交互时间。写入请求链已减少，但读取页面不是全部加速，历史和设置甚至略慢，不能声称问题已解决。

本轮本地3000端口未响应；尚未取得新浏览器trace。不重复运行会写入测试数据的benchmark脚本来冒充只读测量。

## 候选项，需证据排序

- 详情图表依赖拆分/延后非首屏加载，确认实际bundle占比与loading占位避免布局跳动。
- 历史记录按可见窗口加载或分页，避免先读取大量记录再客户端裁切。
- 身份/数据查询复用是否仍存在串行、跨区数据库耗时；保留鉴权，禁止跨用户缓存。
- 现有乐观更新需保留保存中、失败回滚与防重复写入，不能将界面先变色当作已持久化。
